Three directions for the BSGO game control app

Static design proposals dated 2026-10-11. Each one uses a saved game capture from test-data/vision/v1. Readings, findings, and timings are illustrative. They are not live results. Use the state switch to see how each direction handles a normal run, a run that needs you, and a lost game connection.

Proposal
State

A · Mission console: tell it the goal and watch the plan

The app is organised around a mission, such as “Mine Water near the outpost until the hold is full”, rather than individual routines. The mission is shown as a short plan. The app highlights the current step and names any blocker on the step it affects. Scan, approach, and mine become stages of one run instead of separate buttons.

  • The header has one sentence of status, one owner (“You” or “App”), and a large Pause bound to a hotkey.
  • The game view stays large. When the game is missing, it becomes the place to recover.
  • Findings are shown in a sortable table, with the best target highlighted, next to a plain-language activity log.
  • Diagnostics move to a separate screen for engineers and stay out of the operating view.

Best for: the Autopilot future, long unattended runs, and explaining what the bot is doing.

Costs: the controller needs a mission and phase model, which partly exists in mission.py and execution_status.py. It also duplicates the game image on the same monitor.

Replaces: the feature tabs, mode tabs, enable checkbox, scope chips, auto-scan button, action tabs, and Start/Stop. One mission picker and one Start button do the same job.

B · Companion dock: a slim panel docked beside the real game

The app stops copying the game image and docks as a 300 px panel snapped to the side of the BSGO window. You play in the game itself and the dock acts as your co-pilot. Global hotkeys handle the common actions, so you rarely need to leave the game. Alerts appear as toasts near the game.

  • The ring at the top combines status and progress, with one line of text below it.
  • Each of the four actions shows its hotkey. Pause is always the first action.
  • The panel shows the three most useful findings and the three ship readings that matter: hull, energy, and hold.
  • Everything else, including history, diagnostics, and settings, opens in a separate window.

Best for: Assist mode while you are still flying, one-monitor setups, and getting the most game pixels.

Costs: it needs a native always-on-top window or a docking helper. The browser page alone cannot snap to the game. Global hotkeys must not clash with game keys.

Removes: the duplicated game view, the five-tile instrument strip, and the long scrolling rail.

C · Remote pocket: check on the run and intervene from another device

This direction treats the app as true remote game control. The PC runs the bot, and you check it from your phone, tablet, or a second screen on the LAN. The phone gives a quick status view, sends alerts that need a decision, and offers a large Pause. Setup and diagnostics stay on the desktop.

  • Now: a live thumbnail, one status sentence, run progress, three vitals, and Pause and Resume buttons in thumb reach.
  • Alerts: a feed of decisions and events, each with a single action.
  • Summary: what the session produced, shown as a reward-per-time chart.
  • Light theme for daylight readability on a phone. The game stays dark, and the app does not need to match it.

Best for: long Autopilot or NPC-farm sessions where you are away from the PC.

Costs: it needs a LAN-reachable server with authentication or pairing (it is loopback-only today), push notifications, and a safe remote-stop contract. Remote input raises safety stakes, so Pause must be confirmed and acknowledged.

Pairs with: A or B on the desktop. C is a second surface, not a replacement.
